Parte 1:

a) Garantir a integridade dos dados em um banco de dados significa manter todos os dados armazenados consistentes de acordo com o seu tipo e limitações definidas pelo usuário ou sistema e certificar que dados que aparecem em múltiplas tabelas não carreguem valores divergentes.

b) Integridade de entidade:
- Procura garantir que toda linha em um banco de dados relacional seja identificável, ou seja, que ela sempre carregue uma chave primária válida;
- Para que haja integridade em um entidade, é necessário que ela possua uma chave primária válida;
- Não, pois isso pode comprometer a identificação da entidade;
- Não, pelo mesmo motivo do item anterior;
- Caso essas regras não forem respeitadas, há o risco de que entidades se tornem irreferenciáveis e que dados sejam escritos, deletados e acessados erroneamente

Ex: Padeiro(pk nome, fk padaria), Padaria(pk nome)  -> Padeiro("Marco", "Marco's"), Padaria("NULL") Nesse caso, o padeiro carrega uma referência incorreta e a padaria está inacessível.	

c) Integridade referencial:
- Procura garantir que os relacionamentos entre tabelas permançam válidos e coerentes;
- Ela determina que toda chave estrangeira em uma tabela referenciadora obrigatóriamente deve apontar para uma
chave primária na tabela referenciada;
- Não, pois isso comprometeria a integridade referencial;
- Um registro órfão contém uma chave estrangeira que aponta para uma entidade inexistente;
- A exclusão de um registro referenciado por outra tabela pode gerar registros órfãos;

Ex: DEPTO:	Id	n_funcionarios		FUNCIONARIO:	nome	Id_DEPTO	
		10	3					Ana	20
		
- O banco retornará um erro nessa tentativa de cadastro, pois a funcionária Ana referencia um departamento de id 20, que não existe.

d) Integridade de domínio:
- O domínio de um atributo é o conjunto de todos os valores que ele pode assumir;
- Podemos determinar os valores válidos a partir das informações reais que serão representadas. Ex: idade deve ser um inteiro positivo;
- Sim, especificar um tipo de dado restringe o domínio de um atributo;
- Sim, como o mecanismo check, que verifica se um dado atende a um determinado requisito ao invés de analizar o seu tipo.
- Preço deve ser um unsigned float ou equivalente, pois deve ser sempre positivo e ter casas decimais para representar os centavos.
- Estoque deve ser um unsigned int ou equivalente, pois não pode haver estoque negativo e pedaços de produtos não são comercializáveis;

PK 
{
	Procura garantir que todos os elementos de uma tabela sejam identificáveis;
	Diferenciar dois clientes de mesmo nome.
}

FK 
{
	Procura garantir uma interação segura entre tabelas;
	Um elemento de uma tabela precisa de informações de intens em outras tabelas.
}

NOT NULL
{
	Procura garantir que determinado campo não esteja vazio;
	Quando um usuário tenta criar um login sem uma senha.
}

UNIQUE
{
	Procura garantir que não haja valores repetidos em determinado campo;
	Para números de telefone e emails.
}

CHECK
{
	Procura garantir que os valores de determinado campo atendem a certos requisitos;
	Investimentos com aporte mínimo;
}

DEFAULT
{
	Procura garantir que um campo assuma determinado valor caso ele não tenha sido especificado pelo usuário;
	Em qual pasta um aplicativo será instalado;
}
